# 蓝心同行完整开发路线方案

## 0. 项目目标

项目名称：蓝心同行
产品定位：懂你的全旅程 AI 旅游搭子
核心形象：蓝小心
目标形态：运行在 Android / vivo 手机上的移动端 App
核心体验：用户通过文字、图片、语音与蓝小心对话，完成旅行规划、记忆沉淀、主动提醒、旅拍整理、文案生成和旅行复盘。

本项目不是普通攻略生成器，而是一个具备长期记忆、主动陪伴、数字人表达和全旅程闭环的移动端 AI Agent。

最终开发目标按“接近完整产品”推进，但执行上采用阶段式开发：先完成可运行半真实 MVP，再逐步补齐地图、天气、相册、通知、语音、用户系统、云同步等能力。

## 1. 总体技术栈定案

### 1.1 移动端 App

* 框架：Flutter + Dart
* 路由：go_router
* 状态管理：Riverpod
* 网络请求：dio
* 本地数据库：drift + SQLite
* 本地轻量存储：shared_preferences
* 安全存储：flutter_secure_storage
* JSON 模型：freezed + json_serializable
* 图片选择：image_picker
* 相机：camera
* 录音：record
* 音频播放：just_audio
* 通知：flutter_local_notifications
* 定位：geolocator
* 权限：permission_handler
* 动画：GIF / Animated WebP / Lottie
* 数字人表达：蓝小心状态机驱动素材切换

### 1.2 后端服务

* Web API：FastAPI
* Python 环境：uv
* 数据校验：Pydantic
* ORM：SQLModel 或 SQLAlchemy
* 数据库：开发期 SQLite，部署期 PostgreSQL；如果后期服务器压力较大，可切 Supabase / Neon
* Agent 编排：LangGraph
* 模型调用：OpenAI 兼容接口为主，蓝心大模型 API 用于适合其能力的任务
* HTTP 客户端：httpx
* 日志：loguru
* 接口文档：FastAPI 自动 OpenAPI / Swagger
* 测试：pytest
* 部署：Docker Compose + Nginx + HTTPS

### 1.3 模型与工具

* 默认大模型：OpenAI 兼容接口
* 蓝心大模型：用于比赛展示和适合蓝心能力的任务，如记忆抽取、角色化对话、文案生成、ASR/TTS、图片理解等
* 地图：高德地图优先
* 天气：高德天气优先
* POI：高德 POI 优先
* 路线：高德路线 API，App 内以卡片展示，并支持跳转高德/百度地图导航
* 语音：蓝心 ASR/TTS 优先，失败时使用系统 TTS 或降级为文字
* 图片理解：多模型适配器，蓝心多模态、OpenAI 兼容视觉模型、Mock 标签均可切换

## 2. 核心产品边界

### 2.1 必须做的核心闭环

第一优先级必须完成以下闭环：

1. 用户创建旅行或通过对话发起旅行需求。
2. 蓝小心识别用户偏好，生成记忆胶囊。
3. 用户选择保存范围：本地长期记忆、本次旅行记忆、临时使用、不记忆、云同步。
4. 系统更新用户旅行画像。
5. Agent 基于用户画像、目的地、天气、POI、时间、预算生成个性化规划。
6. 出行中通过时间、位置、天气、行程节点触发主动提醒。
7. 蓝小心根据 Agent 状态切换 GIF / WebP / Lottie 动作。
8. 用户拍照或选择照片，加入旅拍候选集。
9. Agent 生成朋友圈、小红书、日记或复盘文案。
10. 旅行结束后生成复盘卡，并沉淀新的记忆和建议。

### 2.2 第一版不做或后置的内容

* 不做后台无感监听所有相册。
* 不做自动发布朋友圈/小红书。
* 不做完整 App 内导航。
* 不做多人实时协作。
* 不做 Live2D 绑定。
* 不在 2C2G 服务器上跑大模型推理。
* 不一开始做复杂管理后台。
* 不把所有记忆默认上传云端。

## 3. 系统架构

### 3.1 架构分层

系统分为五层：

1. Flutter 表现层
   负责蓝小心展示、聊天界面、卡片、页面跳转、权限调用、本地通知、相册和语音交互。

2. 端侧数据层
   使用 drift + SQLite 存储本地记忆、用户画像、旅行记录、聊天摘要、照片候选集和离线复盘。

3. 后端 API 层
   使用 FastAPI 对外提供统一接口，负责用户账号、同步、Agent 调用、地图天气工具、文件上传、语音和图片任务。

4. LangGraph Agent 层
   负责任务路由、记忆抽取、用户确认、规划生成、主动提醒、照片分析、文案生成和复盘生成。

5. 模型与工具层
   通过适配器调用 OpenAI 兼容模型、蓝心大模型、高德地图、天气、POI、ASR/TTS、视觉模型等能力。

### 3.2 数据流

用户输入文字/语音/图片/位置
→ Flutter 获取输入并读取本地用户画像
→ 发送必要且脱敏的上下文到 FastAPI
→ FastAPI 调用 LangGraph
→ LangGraph 判断任务类型并调用模型/工具
→ 返回 replyText、cards、avatarState、memoryCandidates、toolTrace、nextActions
→ Flutter 渲染聊天、卡片和蓝小心状态
→ 用户确认记忆或操作按钮
→ 本地保存，若用户允许则同步到云端

## 4. LangGraph Agent 设计

### 4.1 设计原则

采用“完整总图设计，分阶段实现”的策略。

一开始建立一个 `TravelMateGraph`，包含全部节点定义和状态结构，但每个节点可以先用 Mock / 简化逻辑实现。随着功能稳定，再将记忆、规划、旅拍、复盘等节点抽成子图。

这样既能保证一开始的功能衔接，又能避免后续重构困难。

### 4.2 Graph 总状态

`TravelMateState` 应包含以下字段：

* user_id
* session_id
* trip_id
* auth_mode：guest / logged_in
* sync_mode：local_only / cloud_all / selected_only
* input_type：text / voice / image / location / action
* user_message
* image_refs
* audio_ref
* location
* destination
* trip_context
* user_profile
* local_memory_summary
* cloud_memory_summary
* conversation_summary
* intent
* current_stage：pre_trip / during_trip / post_trip
* memory_candidates
* confirmed_memories
* tool_results
* plan_result
* reminder_result
* photo_analysis_result
* copywriting_result
* review_result
* avatar_state
* emotion
* cards
* reply_text
* voice_text
* next_actions
* tool_trace
* errors

### 4.3 总图节点

第一版节点如下：

1. `input_normalizer`
   统一处理文字、语音、图片、位置、按钮动作。

2. `context_loader`
   读取用户画像、旅行上下文、记忆摘要、同步模式和当前阶段。

3. `intent_router`
   判断用户意图：闲聊、创建旅行、规划、调整路线、确认记忆、上传照片、生成文案、复盘、设置等。

4. `memory_extractor`
   从用户输入中抽取可能影响旅行体验的记忆候选。

5. `memory_confirm_interrupt`
   生成记忆胶囊，等待用户确认保存范围。

6. `memory_writer`
   根据用户选择写入本地记忆、云端记忆或本次旅行记忆。

7. `profile_updater`
   更新结构化用户画像。

8. `trip_context_builder`
   解析目的地、时间、预算、同行人、旅行风格、出发位置等信息。

9. `tool_planner`
   决定需要调用哪些工具：天气、POI、路线、定位、图片理解、ASR、TTS。

10. `tool_executor`
    执行工具调用，返回结构化结果。

11. `trip_planner`
    生成个性化旅行规划。

12. `trip_adjuster`
    根据天气、位置、排队、体力、用户反馈调整行程。

13. `reminder_checker`
    判断是否触发主动提醒。

14. `photo_analyzer`
    分析用户选择或拍摄的照片，生成标签、地点、分享评分。

15. `copywriter`
    生成朋友圈、小红书、日记、Vlog 旁白等文案。

16. `review_generator`
    生成旅行复盘卡，包括路线、照片、任务、记忆和下次建议。

17. `avatar_state_mapper`
    根据任务阶段和情绪决定蓝小心动作状态。

18. `response_composer`
    组装前端响应：文本、语音、卡片、按钮、状态、工具轨迹。

19. `error_fallback`
    模型或工具失败时返回可用降级结果。

### 4.4 后续子图拆分

稳定后可拆为：

* `MemorySubgraph`
* `TripPlanningSubgraph`
* `ReminderSubgraph`
* `PhotoSubgraph`
* `ReviewSubgraph`
* `AvatarExpressionSubgraph`

拆分时保留统一状态字段和统一返回结构，避免前端改动。

## 5. 前端页面路线

### 5.1 必须页面

1. 首页 / 蓝小心空间
   上半屏数字人，下半屏半透明聊天界面，显示状态、默契值、快捷入口。

2. 登录 / 游客模式页
   支持邮箱/手机号 + 密码登录，同时保留“不登录直接使用”。

3. 创建旅行页
   支持表单创建，也支持对话创建。目的地字段应使用 `destination`，不要只写 `city`，因为目的地可能是城市、景区、商圈、区域或多个地点组合。

4. 聊天页
   支持文字、语音、图片输入，展示 Agent 回复、卡片、工具轨迹和蓝小心动作。

5. 记忆胶囊页
   展示待确认记忆、保存范围、本地/云端同步选项、编辑和删除入口。

6. 用户画像页
   展示饮食、节奏、交通、兴趣、预算、表达风格等结构化画像。

7. 出行规划页
   展示路线时间轴、推荐理由、画像匹配点、风险提示、备选方案和地图跳转。

8. 主动提醒页 / 弹窗
   展示触发原因、风险说明、调整方案和蓝小心状态变化。

9. 旅拍候选集页
   支持拍照、选图、标签、评分、删除、生成文案。

10. 文案生成页
    支持朋友圈、小红书、日记、Vlog 旁白等风格切换。

11. 旅行复盘页
    展示今日路线、高光照片、完成任务、状态变化、新增记忆和下次建议。

12. 设置页
    包括人格、主动程度、同步策略、隐私、通知、语音、清空记忆等。

### 5.2 蓝小心状态机

第一版状态：

* idle：待机
* hello：欢迎
* thinking：思考/记忆抽取
* planning：路线规划
* warning：风险提醒
* excited：发现照片/盲盒任务
* tired：疲惫/休息提醒
* happy：复盘/完成任务
* speaking：语音播报

前端根据后端返回的 `avatarState` 切换素材。素材命名不强行规定死，应先扫描实际文件名，再建立映射表。

第一版地图能力做到：

## 9. 用户系统与同步策略

### 9.1 登录方式

第一版支持：

* 邮箱 + 密码登录
* 手机号 + 密码登录
* 游客模式

暂不做短信验证码和第三方登录。

### 9.2 游客模式

游客模式下：

* 可以完整使用旅行规划、记忆胶囊、旅拍候选集、复盘等功能。
* 数据默认只存本地。
* 用户后续登录后，可以选择是否迁移本地数据到云端。

### 9.3 同步模式

用户可选：

1. 本地模式：所有记忆只存在本机。
2. 云同步模式：记忆、画像、旅行记录同步到账号。
3. 部分同步模式：用户逐条选择哪些记忆或旅行记录上云。

开发顺序：

1. 先做本地模式。
2. 再做登录与全量同步。
3. 最后做逐条选择同步。

## 10. 语音与照片方案

### 10.1 语音

第一版实现：

* 用户录音。
* 上传后端 ASR。
* ASR 结果进入聊天输入。
* Agent 回复后生成 TTS。
* App 播放语音。
* 如果 TTS 不稳定，则使用系统 TTS 或只展示文字。

### 10.2 照片

第一版实现：

* 用户主动选择照片。
* App 内拍照。
* 加入旅拍候选集。
* 上传后端分析。
* 生成标签、评分、文案。
* 用户确认后加入复盘。

不做后台无感相册监听。

## 12. 三人协作方式

你们不按前后端固定分工，而是三人同职责、按功能认领。为了避免冲突，采用 Issue 驱动开发。

### 12.1 分支策略

* `main`：稳定可发布版本。
* `dev`：日常集成分支。
* `feat/*`：功能开发。
* `fix/*`：Bug 修复。
* `chore/*`：工程配置。
* `docs/*`：文档。

流程：

1. 从 `dev` 拉功能分支。
2. 一个 Issue 对应一个分支。
3. 完成后开 PR 到 `dev`。
4. 至少一名队友 review。
5. 合并后删除功能分支。
6. 每个阶段结束后从 `dev` 合并到 `main`，打 tag。

### 12.2 Issue 类型

* `feature`：功能开发。
* `bug`：问题修复。
* `ui`：页面和交互。
* `agent`：LangGraph 节点。
* `api`：后端接口。
* `data`：数据库和同步。
* `docs`：文档。
* `demo`：演示材料。
* `test`：测试和验收。

### 12.3 每个功能的验收模板

每个 Issue 必须写清：

* 功能目标
* 涉及页面
* 涉及接口
* 涉及数据库表
* 输入示例
* 输出示例
* 降级方案
* 验收步骤
* 截图或录屏要求

## 13. CI/CD

第一阶段只做 A+B：

1. Flutter analyze。
2. Flutter test。
3. Python ruff / pytest。
4. 后端 Docker build。
5. Android APK 自动构建。

暂不做自动部署，避免 CI/CD 卡住开发节奏。后期再加服务器自动部署。

## 14. 性能与稳定性原则

2C2G 服务器只做后端托管，不跑大模型推理。

后端优化原则：

* 模型调用走外部 API。
* 高德工具调用做缓存。
* 图片上传限制大小。
* TTS 音频缓存。
* 普通聊天使用流式输出。
* 规划和复盘采用分阶段展示。
* 模型失败时返回降级内容。
* 所有外部工具必须有 Mock 兜底。
* 记录 toolTrace，便于调试和比赛展示。
